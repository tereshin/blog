# Research: Платформа публикаций и обсуждений

Решения ниже закрывают технические неизвестные платформы, каркаса разделов и рисунка ленты, статьи и профиля, а также окружений, тестовых данных и тестового входа (FR-123–FR-132). Нумерация FR и SC — по [spec.md](./spec.md).

## Стек и каркас

### 1. Стек

**Decision**: Клиент — React 19 на Vite, TypeScript strict, pnpm workspaces, слои FSD по `react-architecture.mdc`. Маршрутизация — React Router с вложенными маршрутами. Данные — TanStack Query, состояние оболочки — Zustand. Стили — Tailwind CSS 4, компоненты — HeroUI v3 (решение 2). Сервер — Node.js 22, Fastify, Drizzle ORM, PostgreSQL 16 на сервис, NATS JetStream, pino, OpenTelemetry по `node-microservices.mdc`. Вход — собственный OAuth-обмен с Google в `identity-service` через `openid-client`; сессия серверная, cookie ставит `gateway`. Проверка правил — Vitest (+ testcontainers). Сквозные пути — Playwright. Решение принято на сессии уточнений 2026-10-08 вместо Next.js одним процессом.

**Rationale**: Правила `.cursor/rules` задают Vite + FSD для клиента и Fastify-сервисы для сервера как обязательные. Требование «обе боковые карточки есть сразу» клиентское приложение закрывает само: каркас рисуется в первом кадре до ответа сервисов, а центр и списки карточек приходят с заготовками. Серверный рендер для этого не нужен; поисковикам и превью публичные адреса отдаёт `gateway` отдельным ответом (решение 25). Drizzle оставляет документ статьи JSON-полем и даёт явный индекс полнотекстового поиска. Auth.js привязан к фреймворку страниц и не нужен, когда сессию ведёт отдельный сервис.

**Alternatives considered**:

- Next.js App Router одним процессом. Прежнее решение; давал каркас в первом HTML, но спорит с правилами (Vite, `services/*`, `import.meta.env`, FSD-слой `pages/`) и тянет серверный рендер всего приложения ради одного требования к роботам.
- Prisma. Подходит для таблиц, но полнотекстовый вектор и точечные транзакции счётчиков проще оставить в SQL, который Drizzle не прячет.
- Вход паролем или другими поставщиками. Спецификация оставляет только Google.

### 2. Библиотека компонентов

**Decision**: База `shared/ui` — HeroUI v3 (Tailwind CSS 4, React Aria внутри). Каркас берёт из неё `Card`, `Drawer` для панели навигации, `Dialog`, `Tabs`, `Menu`, `Skeleton`, `Button`; карточка статьи — compound-компонент `entities/article/ui/ArticleCard` поверх `shared/ui`. Тёмный и светлый вид образца задаются темой HeroUI (переменные цвета фона, карточки, акцента) и `cva`-вариантами, а не второй библиотекой и не отказом от библиотеки. Сетка зон `Shell` и внутренняя прокрутка карточек — свои, потому что аналога у библиотеки нет. Решение принято на сессии уточнений 2026-10-08 вместо прежнего «без библиотеки».

**Rationale**: Правило `react-components.mdc` требует compound-идиому «как у HeroUI», слоты вместо булевых пропсов (`isOwnProfile` → `<ProfileCard actions={<OwnerActions/>}>`) и готовую доступность для панелей, меню, вкладок и диалога «Купить показы»; писать фокус-ловушку и ARIA руками — нарушение правила. HeroUI v3 построена на React Aria и Tailwind CSS 4, то есть на том же стеке, и не навязывает свой layout.

**Alternatives considered**:

- Свои примитивы поверх React Aria Components. Та же доступность, но compound-идиому и варианты пришлось бы повторять руками; выигрыша в виде нет.
- Без библиотеки, всё своё на Tailwind. Прежнее решение. Доступность диалогов, меню аватара и панели пришлось бы писать вручную — запрещено правилом.

### 3. Один layout-маршрут на все разделы

**Decision**: Все разделы из FR-030 — дочерние маршруты одного родительского маршрута `ShellLayout` в `app/routes/router.tsx`. Шапка, левая карточка и правая карточка рисуются виджетом `widgets/shell` внутри `ShellLayout`; страница раздела (`pages/*`) попадает в `<Outlet/>` центра. Администрирование не получает свой родительский маршрут. Шапка каркаса получает через слот три состояния центра: пилюля первой статьи «Популярного», поле поиска, возврат с усечённым названием статьи.

**Rationale**: Спецификация требует один каркас для ленты, профиля, статьи, сообщений, редактора и администрирования. Родительский маршрут остаётся смонтированным, пока меняются дети: шапка и карточки не размонтируются, их query-кэш не сбрасывается. Второй родительский маршрут завести нельзя без правки `router.tsx` — это заметно на ревью.

**Alternatives considered**:

- Каждая страница сама рисует `<Shell>` вокруг себя. Колонки размонтируются при каждом переходе и мигают; любой раздел может «забыть» обёртку.
- Условный показ колонок внутри `Shell` по текущему маршруту. Прежняя ошибка профиля была именно таким условием.
- Отдельный клиентский маршрутизатор ленты. Прямая ссылка на статью и профиль тогда собирает колонки вторым кадром.

### 4. Прокрутка

**Decision**: Оболочка занимает высоту окна (`100dvh`). Шапка — первая строка сетки и в прокрутку не входит. На ширине от 1200px тело оболочки — три колонки фиксированной высоты. Прокручивается центр. Левая карточка прокручивается внутри себя, когда темы выше неё. Правая карточка остаётся высотой окна; если десять комментариев не влезают, список прокручивается внутри карточки, заголовок карточки остаётся. У обоих внутренних прокруток `overscroll-behavior: contain`. Кнопка возврата наверх вызывает `scrollTo` у прокрутки центра и видна, когда `scrollTop` центра больше нуля.

**Rationale**: Формулировка «возвращается центр», а не окно, требует отдельной прокрутки центра. Липкие колонки на прокрутке всего документа оставляют цепочку прокрутки: колесо над темами увозит страницу и шапку. Высота окна это обрывает.

**Alternatives considered**:

- `position: sticky` у колонок при прокрутке документа. Шапка и длинный центр делят одну прокрутку, а спецификация разделяет прокрутку центра и прокрутку тем.
- Порог в несколько десятков пикселей перед показом кнопки «наверх». Спецификация говорит «центр прокручен вниз», без отдельного порога.

### 5. Узкая ширина и светлый вид

**Decision**: Граница — `min-width: 1200px`, только в CSS. Ниже неё те же узлы: шапка, одна колонка центра, левая навигация в одной панели по той же кнопке шапки, правая карточка в потоке под содержимым центра; у «Написать» остаётся перо без слова, длинный центр шапки скрыт; на профиле «Редактировать», статистика и настройки переносятся под имя, если не помещаются в строку аватара. Пересечение 1200px не меняет маршрут и не размонтирует каркас. На узкой ширине прокрутка, которую возвращает кнопка «наверх», — общая колонка центра вместе с правой карточкой под ним. Состав и порядок блоков в светлом и тёмном виде одни. Тёмный вид: почти чёрный фон, тёмно-серые карточки, белый текст, серый вторичный, синий акцент, зелёная репутация. Светлый: светло-серый фон, белые карточки, почти чёрный текст, те же синие акценты.

**Rationale**: FR-037 запрещает особое исключение раздела; FR-041 требует тот же состав в светлом виде. Одна разметка с разными областями сетки и одной темой не даёт профилю остаться без колонок или спрятать блок при смене вида.

**Alternatives considered**:

- Отдельное мобильное дерево компонентов или второй набор компонентов на светлом фоне. Два дерева расходятся в первом же новом блоке.
- Контейнерный запрос вместо окна. Спецификация меряет ширину окна, не карточки.

### 6. Подсветка пункта

**Decision**: Чистая функция от вида раздела (`widgets/shell/lib/section-highlight.ts`). «Популярное», «Свежее» и «Моя лента» подсвечивают свой режим. Тема и статья подсвечивают тему статьи или страницы темы. «Сообщения» и «Рейтинг» подсвечивают свои пункты. Профиль, закладки, поиск, «О проекте», редактор, списки подписчиков и подписок, модерация, темы площадки и настройки площадки не подсвечивают никого. Если тема статьи архивная и её нет в левом списке, подложку не получает никто.

**Rationale**: FR-053 задаёт это таблицей, а не побочным эффектом последнего клика. Функция тестируется без браузера. Хранить «последний выбранный пункт» нельзя: прямая ссылка на профиль иначе оставила бы подсветку ленты.

**Alternatives considered**:

- Подсветка по совпадению URL-префикса. У профиля, статьи и темы разные префиксы, а статья должна подсвечивать тему, которой в её URL нет.

### 7. Загрузка центра, пустые состояния и пустая правая карточка

**Decision**: Страницы `pages/*` подключены через `React.lazy`; `ShellLayout` оборачивает только `<Outlet/>` центра в `Suspense` с `CenterSkeleton` той же ширины. Пока центр ленты, статьи или профиля не получен, на его месте серые заготовки той же формы, что итоговые карточки. Каркас в эту границу не входит. Списки тем и популярных комментариев ждут данные внутри своих карточек своими состояниями `loading` / `empty` / `error`. Правая колонка сетки задана и при пустом списке; внутри карточки — пустое состояние. Колонка не получает `display: none` и не переводится в нулевую дорожку. Ошибка загрузки объясняет сбой и даёт повторить; пустая лента, пустые комментарии и пустой профиль объясняют, что данных нет, и отличаются от ошибки.

**Rationale**: FR-034, FR-036, FR-118. Если данные колонок ждать на уровне `ShellLayout`, первая загрузка подменит весь каркас. Если пустой список не рисовать, центр заберёт ширину. Пустой экран без формы карточки выглядит как сбой.

**Alternatives considered**:

- Один `Suspense` вокруг всего `App`. Он закрывает и шапку, и колонки.
- Не рендерить правую карточку без комментариев. Это схлопывание, которое спецификация запрещает.
- Один общий индикатор вместо заготовок. Форма карточек на время загрузки пропадает.

### 8. Панели поверх раздела

**Decision**: Уведомления, статистика, вход, «Купить показы», подтверждения и предупреждение об уходе из редактора — `Dialog`/`Drawer` из HeroUI поверх текущего маршрута, без смены адреса. Панель входа открывает и событие `sessionEvents 'expired'` из http-клиента (`401` в любом запросе), не стирая несохранённый текст. Поиск в шапке открывает поле на месте центра шапки; результаты поиска — раздел `/search` внутри того же каркаса.

**Rationale**: FR-035 и крайний случай редактора. Смена маршрута на время панели оставила бы после закрытия другой каркас или другую прокрутку. Отдельный адрес панели показов не нужен.

**Alternatives considered**:

- Отдельный маршрут для каждой панели. Нужен для адресуемой панели, но колокольчик, статистика, показы и подтверждение ухода адресом не являются.

### 9. Откуда колонки берут записи

**Decision**: Левая карточка читает активные темы — `GET /v1/topics` через `gateway` из `content-service`. Правая читает до 10 популярных комментариев, которые этот человек может читать, — `GET /v1/comments/popular` из `discussion-service`. Это два независимых запроса TanStack Query с `staleTime` ≥ 30 с и общими ключами `topicKeys.list()` и `commentKeys.popular()` на всех разделах; смена раздела их не перезапрашивает. Пока сервисов нет, Playwright и Storybook поднимают фикстурный `gateway` (MSW) с тем же контрактом. Пустой ответ показывает пустое состояние, а не выдуманные комментарии.

**Rationale**: Один ключ запроса на все разделы гарантирует «тот же набор, что на главной» (FR-067). Два отдельных источника — следствие решения о сервисах: задержка обсуждения не трогает темы, и наоборот.

**Alternatives considered**:

- Один «снимок колонок» одним запросом. Связывал бы два сервиса в один вызов на `gateway` и превращал задержку любого из них в задержку обеих карточек.
- Отдельный запрос популярных комментариев на каждый раздел. На профиле и в редакторе легко получить другой набор.

### 10. Состояние оболочки и прокрутка в коде

**Decision**: `useShellStore` (Zustand) хранит `is_nav_open` и `center_scroll_top`; потребители читают срезами (`useShellStore(s => s.is_nav_open)`). Прокрутка центра пишется в стор через `requestAnimationFrame`-троттлинг, а `BackToTop` читает только булев срез `center_scroll_top > 0`, чтобы не перерисовываться на каждый пиксель. Подсветка — чистая функция без стора.

**Rationale**: `react-performance.mdc`: состояние близко к месту использования, чтение срезами, никаких объектов в контексте, который меняется на каждый скролл.

**Alternatives considered**:

- Контекст React с объектом состояния оболочки. Каждое изменение прокрутки перерисовывало бы шапку и обе карточки.

## Сервисы, сессия и события

### 11. Границы сервисов

**Decision**: Семь сервисов за одним входом: `gateway`, `identity`, `content`, `discussion`, `messaging`, `notification`, `media`. У каждого, кроме `gateway`, своя база PostgreSQL. Браузер видит только `gateway`. Каждый сервис — один процесс на контейнер, масштабируется репликами; поток событий держит `gateway`, и его реплики читают брокер, поэтому соединение зрителя не привязано к процессу, который записал комментарий. Распределение сущностей — [data-model.md](./data-model.md), раздел «Владение данными».

**Rationale**: Решение владельца на сессии уточнений. Правило требует database-per-service и общение только через контракты, поэтому «одна база на всех» не вариант. Открытая страница должна увидеть комментарий в течение 2 секунд: запись → outbox → брокер → `gateway` → SSE укладывается в этот срок.

**Alternatives considered**:

- Один сервис-монолит по структуре правила. Предложен как рекомендация и отклонён владельцем.
- PostgreSQL `NOTIFY` вместо брокера. Работает в одном процессе с одной базой; при шести базах и репликах `gateway` нужен общий брокер.
- Опрос каждые 2 секунды. Тысяча читателей даёт постоянную нагрузку даже когда ничего не изменилось.

### 12. Сессия и доступ между сервисами

**Decision**: `GET /v1/auth/google` на `gateway` → `identity` строит адрес Google с `state` и PKCE → callback на `identity` обменивает код, находит или создаёт участника по `sub`, создаёт строку сессии и возвращает `gateway` её идентификатор → `gateway` ставит cookie `HttpOnly; Secure; SameSite=Lax`. На каждом запросе `gateway` проверяет сессию в `identity` (кэш 30 с с инвалидацией по событию `identity.session.revoked`) и передаёт сервисам подписанный служебный JWT с коротким TTL: `user_id`, `role`, `is_restricted`, `can_publish`. Сервисы доверяют только этой подписи, не внутренней сети. Выход — `POST /v1/auth/logout`: `identity` помечает сессию отозванной и публикует событие; `gateway` чистит cookie; клиент сбрасывает query-кэш и шлёт `BroadcastChannel('session')`, остальные вкладки переходят в гостя. Ограничение участника отзывает все его сессии. CSRF — double-submit: не-HttpOnly cookie + заголовок `X-CSRF-Token`.

**Rationale**: `session-security.mdc`: секретов в браузере нет, cookie ставит и читает только вход; `node-microservices.mdc`: между сервисами подписанные служебные JWT. FR-010 и FR-011 требуют выхода во всех вкладках и панели входа без потери текста — это `401` в любом запросе → `sessionEvents 'expired'` → диалог поверх раздела.

**Alternatives considered**:

- Bearer-токен в памяти клиента с refresh-cookie. Допустимо правилом, но cookie-сессия названа предпочтительной и проще для SSE (браузер сам прикладывает cookie к `EventSource`).
- Проверять cookie в каждом сервисе. Дублирует логику сессии в шести местах и даёт сервисам доступ к cookie браузера.

### 13. Живые обновления

**Decision**: Сервис-владелец пишет изменение и событие в свою таблицу `outbox` одной транзакцией; воркер outbox доставляет событие в NATS JetStream (`<context>.<entity>.<past-tense>`, например `discussion.comment.created`, с `event_id`, `occurred_at`, `correlation_id`, `causation_id`, `version`). `gateway` подписан на эти события и держит `GET /v1/events` — поток серверных событий, в который кладёт только тип и идентификаторы, отфильтрованные по правам зрителя (черновик и закрытая статья в чужой поток не попадают; сужение доступа шлёт сигнал, по которому клиент убирает текст). Клиент заново читает затронутые ключи TanStack Query; сигнал перечитывает только затронутую карточку, не всю ленту. Входящие сигналы буферизуются и применяются раз в 50–100 мс; переподключение `EventSource` — с экспоненциальным backoff и jitter, после восстановления клиент перечитывает открытые статью, ленту, колокольчик и диалог (SC-024). Потребители событий в других сервисах идемпотентны по `processed_events(event_id)`.

**Rationale**: `node-microservices.mdc`: публикация только через outbox, доставка at-least-once, идемпотентные потребители. Повторное чтение показывает то, что уже сохранено, поэтому принятый комментарий не теряется при обрыве кадра. Две секунды SC-009 на цепочку хватает: воркер outbox опрашивает таблицу каждые 200–500 мс.

**Alternatives considered**:

- Тащить в событии весь текст. Упирается в размер и расходится с уже записанной строкой, если запись откатилась.
- `publish()` сразу после записи, без outbox. Теряет событие при падении между строками — запрещено правилом.
- WebSocket на отдельном порту. Тот же смысл, второй протокол и второй вход.
- Перезапрос всей ленты на каждый сигнал. Тысяча читателей превращает один комментарий в тысячу чтений ленты.

### 14. Первый суперадминистратор и регистрация

**Decision**: Почта Google первого суперадминистратора задаётся окружением до открытия. Его вход создаёт или поднимает учётную запись даже при закрытой регистрации. Любая другая новая учётка при закрытой регистрации не создаётся, человек видит объяснение. Уже созданная учётка входит. Ограниченный входит и читает, но публикация, комментарий, реакция, подписка, закладка и сообщение отклоняются.

**Rationale**: FR-002 и FR-005. Идентичность для повторных входов — стабильный `sub` Google. Почта нужна, чтобы узнать назначенного суперадминистратора при первом входе. Уточнение решением [36](#36-время-в-seed-порядок-запуска-и-prod-минимум): учётная запись суперадминистратора создаётся командой `bootstrap-prod` заранее, с пустым `google_sub`, и первый вход с подтверждённой назначенной почтой привязывает `sub`.

**Alternatives considered**:

- Создавать суперадминистратора только вручную в базе. Его нельзя назначить до первого входа, а спецификация требует вход заранее указанной учётной записью.

## Лента, реакции и профиль

### 15. Лента как список

**Decision**: `GET /v1/feed?mode=fresh|popular|mine|topic:{slug}&cursor=` возвращает порцию из 20 карточек и `next_cursor` (курсор — `published_at, id`; у «Популярного» — `score, id`). Клиент — `useInfiniteQuery` с ключом `articleKeys.list(mode)`; карточки хранятся нормализованно (`article_by_id` + порядок) и виртуализируются `@tanstack/react-virtual`, когда их больше 100. Следующая порция подгружается заранее, при приближении к концу. Реакция, подписка и закладка — оптимистичные мутации с откатом и точечной инвалидацией `articleKeys.detail(id)`.

**Rationale**: `react-performance.mdc`: курсорная пагинация, виртуализация длинных списков, нормализация, оптимистичные обновления, инвалидация по точным ключам. SC-017 и SC-021.

**Alternatives considered**:

- Пагинация по `offset`. Сдвигается при новой публикации и запрещена правилом.

### 16. Реакция вместо лайка

**Decision**: Одна строка реакции на пару участник–объект в `discussion-service`. Вид — один из четырёх: `laugh`, `heart`, `thumb`, `fire`. На карточке и под статьёй видны только виды, которые уже поставили, и кнопка добавления. Нулевые виды не показываются. Выбор другого вида заменяет прежний. Повтор того же снимает отметку. Гость получает предложение войти. Уведомление автору статьи (FR-106) отправляется при реакции на статью; реакция на комментарий уведомление не создаёт. Отдельной сущности «лайк» нет.

**Rationale**: Спецификация закрывает набор и запрещает две одновременные отметки одного человека. Две таблицы «лайк» и «реакция» разошлись бы в счётчике.

**Alternatives considered**:

- Сначала таблица лайков, потом миграция в реакции. Образец всё равно выкинет лайк, а счётчики придётся склеивать.
- Четыре независимые отметки на человека. Противоречит правилу «прежняя снимается».
- Показывать все четыре вида с нулями. Спецификация оставляет только кнопку добавления, пока реакций нет.

### 17. Счётчики реакций и копии в контенте

**Decision**: Реакции, комментарии, просмотры и закладки принадлежат `discussion-service`. Число на статье и комментарии пересчитывается в той же транзакции, что вставка или снятие: уникальная пара участник–объект не даёт второй отметки, затем счётчик становится равным числу строк, и в том же outbox уходит `discussion.article_counters.updated` с итоговыми числами. `content-service` держит копию `reaction_count`, `comment_count`, `view_count`, `bookmark_count` на статье для карточек ленты и обновляет её по этому событию (идемпотентно: берёт число из события, не прибавляет). Открытая статья и карточка получают сигнал через `GET /v1/events` и перечитывают числа у `discussion`.

**Rationale**: SC-016 запрещает разошедшийся счётчик: источник правды один — строки в `discussion`. Копия в `content` нужна, чтобы лента не делала запрос к `discussion` на каждые 20 карточек (правило: денормализовать по событиям, а не читать синхронно); расхождение копии ограничено доставкой события и укладывается в 2 секунды SC-009.

**Alternatives considered**:

- Только прибавлять и вычитать единицу. Два одинаковых запроса одного человека удваивают число, если уникальность не проверена первой.
- Собирать карточку ленты в `gateway` из `content` и `discussion` на каждый запрос. Два hop-а на каждый экран ленты и отказ ленты при отказе обсуждения.

### 18. Как собирается «Популярное»

**Decision**: В список входят статьи, которые зрителю можно читать, и которые либо опубликованы не раньше чем 7 суток назад, либо имеют не истёкшее продвижение. Порядок — по убыванию суммы реакций и комментариев. Свежая лента и страница темы — те же видимые статьи от новых к старым. «Моя лента» — новые статьи авторов и тем, на которые человек подписан. Отбор делает модуль `feed` в `content-service` по своим копиям счётчиков.

**Rationale**: FR-055 держит обычное «Популярное» на семи сутках и отдельно оставляет продвигаемую статью на весь срок пакета. Сумма реакций и комментариев повторяет формулировку спецификации, без скрытых весов.

**Alternatives considered**:

- Только последние 7 суток, а продвижение лишь поднимает статью внутри них. Тогда пакет не выполняет «оставаться в списке все 7 дней», если статья старше окна.
- Персональные веса. В объёме нет рекомендаций по интересам.

### 19. Продвижение без денег

**Decision**: Панель «Купить показы» — диалог поверх текущего раздела. До подтверждения на ней прямо сказано, что деньги не списываются. Подтверждение записывает `confirmed_at` и `until = confirmed_at + 7 суток` в `content-service`. Повторное подтверждение заменяет срок новыми семью сутками от этого нажатия, а не прибавляет остаток. Полосу охвата видит только автор: над текстом своей статьи и внутри карточки списка своего профиля.

**Rationale**: Допущение спецификации повторяет вид образца и запрещает оплату. Диалог поверх раздела уже предусмотрен каркасом, отдельный адрес панели не нужен.

**Alternatives considered**:

- Платёжный провайдер с нулевой ценой. Это всё равно платёжный контур, которого спецификация не просит.
- Складывать остаток и новые семь суток. Спецификация явно велит отсчитывать от нового подтверждения.

### 20. Просмотр статьи и просмотренное в ленте

**Decision**: Это разные факты. Просмотр для счётчика — строка `(article_id, viewer_key, counted_at)` в `discussion-service`. У участника ключ — его учётная запись. У гостя — случайный ключ в cookie этого устройства. Вставка или обновление старше 30 минут увеличивает счётчик на один; повтор внутри окна не увеличивает; автор статьи и открытие из модерации запись не создают. Полоса «Скрыто N просмотренных поста» считает статью просмотренной в этой ленте, если человек открыл её страницу или нажал «Показать полностью». Ключ хранения — зритель и режим ленты (`fresh`, `popular`, `mine` или тема); список лежит в базе `discussion`. Крестик прячет саму полосу до следующего визита и не возвращает карточки; «визит» — сессия браузера, признак закрытой полосы лежит в `sessionStorage`. Нет просмотренных — полосы нет и место под неё не резервируется.

**Rationale**: FR-091 и FR-066 описывают разные пороги. Общий флаг смешал бы «развернул в ленте» с засчитанным просмотром и окном 30 минут. Уникальная пара статья–зритель сериализует два одновременных открытия.

**Alternatives considered**:

- Считать каждое открытие страницы. Ломает окно 30 минут.
- Хранить просмотры только в cookie. Другое устройство того же участника создаст лишний просмотр, а спецификация для вошедшего считает человека, не устройство.
- Прятать карточки по счётчику просмотров. Раскрытие в ленте тогда полосу не кормит.
- Хранить и список, и крестик только в сессии. После нового визита спецификация снова показывает полосу, но карточки остаются скрытыми — значит список переживает визит.

### 21. Возврат из статьи

**Decision**: Обычный переход в другой раздел начинает центр сверху. Исключение — возврат в шапке статьи. Если в этой сессии человек пришёл из ленты, возврат открывает тот же режим и восстанавливает прокрутку центра. Если статью открыли прямой ссылкой и истории ленты в сессии нет, возврат открывает «Свежее» с начала. Прокрутка хранится в `sessionStorage`, не в базе.

**Rationale**: FR-046 требует вернуть место в ленте. Общее правило «новый раздел сверху» остаётся для остальных переходов, иначе профиль и сообщения наследовали бы чужую прокрутку.

**Alternatives considered**:

- Всегда `history.back`. С прямой ссылки уводит с площадки.
- Всегда «Свежее» сверху. Теряет место в ленте, из которой человек пришёл.

### 22. Репутация и знаки

**Decision**: Репутация — число текущих реакций на опубликованные статьи и комментарии этого человека. Считает её `discussion-service` в транзакции реакции и публикует `discussion.reputation.updated`; `content-service` держит копию на профиле для карточки профиля и рейтинга. Снятие реакции уменьшает число. На экран попадает не меньше нуля: положительное с плюсом, ноль как `0`. Знаки не хранятся отдельной выдачей. «Первый пост» — есть хотя бы одна опубликованная статья (`content`). «10 реакций» — репутация не меньше 10. «Год на площадке» — с `created_at` участника прошёл год (копия даты из `identity.user.created`). Показываются только полученные. Нажатие называет знак.

**Rationale**: Спецификация определяет репутацию как полученные реакции, а не как валюту. Источник правды — строки реакций у их владельца; отдельная таблица знаков разошлась бы с этим числом в момент снятия реакции.

**Alternatives considered**:

- Хранить репутацию счётчиком, который никогда не уменьшается. Спецификация требует уменьшения при снятии реакции.
- Выдавать знаки вручную. В объёме три автоматических условия.

### 23. Подписка и закладка

**Decision**: Подписка — связь участника с автором или с темой в `content-service`. Своя карточка и свой профиль кнопку подписки на себя не показывают. Повторное нажатие снимает подписку. Закладка — статья, которую этому человеку можно читать, в `discussion-service`. Число на карточке равно числу людей, у которых закладка сейчас стоит. «Поделиться» копирует адрес статьи и показывает короткое подтверждение. Жалоба создаёт запись модерации в `content-service`.

**Rationale**: Без этих строк кнопки образца нечего сохранять. Проверка «можно читать» не даёт заложить черновик или закрытую статью.

**Alternatives considered**:

- Подписка только на автора. Страница темы тогда нечем кормит «Мою ленту», хотя FR-056 включает и темы.

### 24. Числа, время и шапка

**Decision**: Число от 1000 сжимается до одной десятой и буквы языка интерфейса: русский «К» и «М», английский и сербский `K` и `M`. Время сегодняшней статьи — часы и минуты. Более старая — день.месяц.год. Длинный заголовок в пилюле шапки и в шапке статьи обрезается многоточием в одну строку. Пилюля на главной — название первой статьи текущего «Популярного», не поле поиска и не «Написать».

**Rationale**: FR-045 и FR-063 задают это явно. Сербский интерфейс латиницей, поэтому буква латинская, как в английском каталоге.

**Alternatives considered**:

- Всегда английские K и M. Спецификация просит букву языка интерфейса.
- Поле поиска по центру шапки постоянно. Образец и FR-045 отдают центр пилюле, поиск открывается отдельно.

## Содержание, доступ и площадка

### 25. Ответ роботам и превью ссылок

**Decision**: `gateway` различает роботов и клиенты превью по `User-Agent` (список: Googlebot, Bingbot, YandexBot, Twitterbot, facebookexternalhit, TelegramBot, Slackbot, LinkedInBot, Discordbot, WhatsApp) и для `/p/{slug}`, `/t/{slug}`, `/u/{slug}` отдаёт отдельный HTML: `<title>`, `meta description`, Open Graph (`og:title`, `og:description`, `og:image`, `og:type`) и для статьи — текст блоков в простой разметке. Данные читаются из `content-service` тем же правилом видимости, что и для гостя: черновик, скрытая и закрытая статья отдают только нейтральный заголовок площадки без содержимого (FR-119). Человек с любым `User-Agent` получает `index.html` приложения. Остальные адреса отдают роботам только метатеги площадки.

**Rationale**: Решение сессии уточнений: индексация и превью нужны, полный серверный рендер — нет. Один модуль на входе не трогает клиентское приложение.

**Alternatives considered**:

- Серверный рендер всего приложения. Противоречит выбору Vite SPA и тянет второй рендер каждого компонента.
- Предрендер статики по расписанию. Отстаёт от правок и смены доступа.

### 26. Документ статьи

**Decision**: Редактор — Editor.js, подключённый только в браузере. На сервер уходит JSON блоков. Разрешённые блоки: абзац, заголовок, список (маркированный, нумерованный, вложенный, проверочный), цитата, выноска, разделитель, код, код внутри строки, выделение, ссылка, изображение с подписью, внешнее медиа из известного списка сервисов, таблица, вложение, карточка человека. Перед записью сервер оставляет во встроенном тексте только `b`, `i`, `u`, `code`, `mark`, `a` со ссылкой `http`, `https` или `mailto` и `br`. Внешнее медиа хранит имя сервиса и адрес источника. Страница собирает предпросмотр из известного шаблона этого сервиса, а не из HTML автора.

**Rationale**: Заказчик назвал Editor.js, а перечень FR-076 совпадает с его инструментами. JSON не даёт автору вставить разметку, которая меняет окружающую страницу. Санитайзер на сервере закрывает обход редактора прямым запросом.

**Alternatives considered**:

- HTML-редактор с очисткой. Очистка HTML шире и легче пропустить атрибут, который двигает вёрстку.
- Свой редактор блоков. Повторяет уже существующий набор инструментов.

Инструменты редактора: `@editorjs/header`, `@editorjs/list`, `@editorjs/quote`, `@editorjs/warning`, `@editorjs/delimiter`, `@editorjs/code`, `@editorjs/inline-code`, `@editorjs/marker`, `@editorjs/underline`, `@editorjs/image`, `@editorjs/embed`, `@editorjs/table`, `@editorjs/attaches`, `@editorjs/personality`. Ссылка внутри текста — встроенный инструмент абзаца, не карточка ссылки.

### 27. Короткий адрес

**Decision**: Одна таблица занятых адресов на профили, темы и статьи. Адрес — 3–40 знаков: строчные латинские буквы, цифры и дефисы, не с дефиса и не на дефис. Занятый и служебный адрес отклоняется, прежний остаётся. Начальный адрес статьи строится из заголовка: кириллица переводится в латиницу местной таблицей, прочее сжимается в дефисы, длина обрезается до 40. Если после этого короче 3 знаков, к основе добавляется публичный номер, пока не станет уникальным. Профиль без адреса открывается по публичному номеру учётной записи, не по внутреннему ключу.

**Rationale**: FR-014 требует уникальности среди всех таких адресов, хотя в URL они стоят под `/u`, `/t` и `/p`. Общая таблица не даёт профилю и статье занять одну строку. Служебные слова совпадают с первыми сегментами контракта разделов: `popular`, `feed`, `messages`, `rating`, `bookmarks`, `search`, `about`, `write`, `admin`, `api`, `auth`, `t`, `p`, `u`.

**Alternatives considered**:

- Уникальность только внутри своего типа. Противоречит FR-014.
- Готовая библиотека транслитерации на все алфавиты. Для русского и сербского заголовка хватает одной таблицы в репозитории.

### 28. Доступ к статье

**Decision**: Видимость — `public`, `members` или `author`. Каждая выборка ленты, поиска, темы, профиля, правой карточки, закладок, уведомления и прямого адреса проходит одну функцию «этот зритель может читать». Чужой ответ не содержит текст, блоки и фрагмент. Сужение доступа шлёт событие статьи; открытый клиент убирает текст без перезагрузки. Администратор читает статью `author` и скрытую статью. Черновик читает только автор.

**Rationale**: FR-102 и FR-103 требуют одного правила на всех поверхностях. Проверка только на странице статьи оставит текст в поиске и в правой карточке.

**Alternatives considered**:

- Фильтр в каждом запросе своими условиями. Расходятся при первой новой поверхности.
- Отдавать текст и прятать его стилем. Текст остаётся в ответе.

### 29. Поиск и язык интерфейса

**Decision**: Поиск статей, людей и тем живёт в `content-service`: полнотекстовый вектор PostgreSQL в конфигурации `simple` плюс индекс триграмм для имени и короткого адреса; профили и темы — его же таблицы, поэтому `GET /v1/search` не ходит в другие сервисы. Результаты проходят ту же функцию видимости. Язык интерфейса хранится одной настройкой `ru`, `en` или `sr` в настройках площадки (`content-service`) и не входит в URL; клиент читает её при старте и по событию `content.settings.updated`. Каталоги надписей лежат в `apps/web/src/shared/i18n`, полные на трёх языках. Нет ключа — показывается русский. Сербский каталог записан латиницей. Смена языка видна со следующей загрузки раздела. Тексты статей, комментариев, имён и тем не переводятся.

**Rationale**: Тексты людей остаются на языке автора, поэтому словарь одного языка их режет. `simple` ищет слово из заголовка на любом из трёх. Префикс локали в адресе сломал бы контракт `/`, `/p/{slug}` и `/u/{slug}`. Отдельный `search-service` отклонён на сессии уточнений.

**Alternatives considered**:

- Отдельный поисковый сервис. Для слова в заголовке и тысячи читателей базы контента достаточно; выделяется, когда появится поиск по комментариям или сообщениям.
- Язык в адресе или в учётной записи читателя. Спецификация задаёт один язык площадки.

### 30. Файлы

**Decision**: `media-service` принимает `POST /v1/media` потоком (`stream.pipeline`, явный `bodyLimit`), проверяет тип по содержимому: изображение — JPEG, PNG, WebP или GIF до 8 МБ, вложение — PDF, DOC, DOCX или TXT до 20 МБ. Байты уходят в S3-совместимое хранилище (MinIO локально), в базе сервиса — только метаданные. Отказ не затирает прежний файл. Имя объекта генерирует сервер. В документ попадает только полученный адрес. Логотип, аватары и обложки — те же правила изображения.

**Rationale**: Границы заданы допущениями спецификации. Проверка типа по содержимому, а не только по расширению, не даёт положить исполняемый файл под видом картинки. Потоковая запись — требование правила к большим телам.

**Alternatives considered**:

- Принимать файлы в `content-service`. Другой профиль нагрузки и памяти; правило называет это основанием для отдельного сервиса.
- Принимать любой файл до лимита размера. Спецификация список типов закрывает.

## Окружения и тестовые данные

### 31. Состав `infra/` и Compose-файлы

**Decision**: Папка `infra/compose/` содержит базовый `docker-compose.yml` и по одному файлу на окружение (`.local.yml`, `.dev.yml`, `.prod.yml`). База описывает всё общее: шесть PostgreSQL 16 (`identity-db` … `media-db`), `nats` с JetStream, `minio` и одноразовый `minio-init` (bucket `media`), семь сервисов, для каждого сервиса с базой — одноразовая `<service>-migrate`, клиент `web`. Файл окружения меняет только то, чем окружения отличаются: `local` собирает образы из исходников и публикует порты баз, `mock-google` и малый seed; `dev` берёт образы из реестра, держит порты баз закрытыми и добавляет `mock-google`; `prod` берёт образы из реестра, ставит `restart: unless-stopped`, лимиты памяти и публикует только порты клиента и `gateway`. Запуск — `pnpm infra:up <local|dev|prod>`, который собирает `-f base -f env --env-file infra/env/<env>.env`. `docker compose up` ждёт готовности по `depends_on` с `service_healthy` (базы, NATS, MinIO) и `service_completed_successfully` (миграции, bucket). Образы всех семи сервисов собираются из `infra/docker/service.Dockerfile` с `ARG SERVICE`.

**Rationale**: FR-123–FR-126. Миграции отдельной задачей — требование `node-microservices.mdc` («не на старте каждой реплики»); Compose выражает порядок без собственного оркестратора. Одна команда поднимает всё (FR-125), потому что зависимости заданы, а не запускаются руками по списку.

**Alternatives considered**:

- Один файл с профилями Compose (`--profile prod`). Выглядит короче, но смешивает три набора портов и ограничений в одном файле, и ошибочный флаг в `prod` поднимет `mock-google`. Раздельные файлы позволяют проверить состав `prod` статически.
- `docker-compose.yml` в корне. Прямо запрещено FR-123.
- Kubernetes или Nomad. Исключено FR-124.

### 32. Клиент в контейнере и внешний вход

**Decision**: `infra/docker/web.Dockerfile` собирает `apps/web` Vite-ом и кладёт `dist` в `nginx-unprivileged` с SPA-fallback на `index.html`; контейнер отдаёт только статику. Адрес `gateway` в сборку приходит через `VITE_API_BASE_URL` (не секрет, читается только в `shared/config/env.ts`). В `local` и `dev` он абсолютный (`http://localhost:3000`, адрес dev-сервера), `gateway` разрешает CORS с credentials для `WEB_ORIGIN`; cookie общая для портов одного хоста, CSRF-cookie читается клиентом. В `prod` адрес пустой — один origin, за который отвечает внешний вход вне репозитория; требования к нему перечислены в [environments.md](./contracts/environments.md): `/v1/*` и SSE → `gateway`, запросы поисковых роботов и превью к публичным адресам → `gateway` (`prerender`), остальное → клиент, TLS и `Secure`-cookie.

**Rationale**: FR-126 исключает обратный прокси из состава, но оставляет «клиентское приложение со своим веб-сервером для статики». Проксирование `/v1` внутри контейнера клиента было бы тем же обратным прокси, спрятанным в `nginx.conf`, и потребовало бы второго потока SSE через лишний hop. `gateway` статику не раздаёт: он остаётся единственным входом для данных и не получает обязанностей, не связанных с сессией и маршрутизацией (прежняя задача выдачи через `WEB_DIST_DIR` отменена).

**Alternatives considered**:

- Раздавать статику из `gateway`. Мешает независимому релизу клиента и нарушает «один сервис — одна ответственность».
- Встроить в nginx клиента `proxy_pass /v1`. Скрытый обратный прокси, вне FR-126.
- Конфигурация клиента из `/config.js` в рантайме. Позволила бы один образ для всех окружений, но добавляет второй путь чтения конфигурации мимо `import.meta.env`; образы клиента строятся на каждое окружение.

### 33. Конфигурация, секреты и проверка окружения

**Decision**: Каждое окружение читает один файл `infra/env/<env>.env`. В репозитории — только `local.env.example`, `dev.env.example`, `prod.env.example` с заглушками (`CHANGE_ME`), в `.gitignore` добавляются `infra/env/*.env` (шаблон `.env.*` корневого `.gitignore` файлы вида `local.env` не покрывает). `APP_ENV` (`local`, `dev`, `prod`) — обязательная переменная каждого сервиса, читается только в `config/env.ts`. Значения, которые нельзя оставить заглушкой в `prod` (`SERVICE_JWT_PRIVATE_KEY`, `GOOGLE_CLIENT_SECRET`, пароли баз, ключи MinIO), проверяются при старте: заглушка в `prod` роняет сервис. Для запуска одного сервиса с хоста (`pnpm --filter … dev`) есть `local.host.env.example` с теми же ключами и адресами `localhost`. `pnpm infra:up prod` отказывается стартовать, если `infra/env/prod.env` отсутствует или содержит `CHANGE_ME`.

**Rationale**: FR-125 запрещает секреты в репозитории; `session-security.mdc` — секреты вне бандла и репозитория; `node-microservices.mdc` — отсутствие обязательной переменной роняет процесс.

**Alternatives considered**:

- Docker secrets как файлы. Правильнее, чем переменные окружения, но для одного сервера и ограничения «минимум» оставлено на потом; `config/env.ts` позже может читать `*_FILE`, не меняя остальных.
- Общий `.env` в корне. Смешивает окружения; один неверный файл в `prod` стал бы незаметным.

### 34. Тестовый вход: `mock-google`

**Decision**: `infra/mock-google` — маленький OIDC-провайдер на Fastify и `jose` в собственном контейнере, есть только в `local` и `dev`. Он публикует `/.well-known/openid-configuration`, `GET /authorize`, `POST /token`, `GET /jwks`. `GET /authorize` показывает страницу со списком seed-участников из `packages/seed-data` (суперадминистратор, администратор, автор, читатель, ограниченный, без права публикации, новый), выбор выдаёт одноразовый `code` с учётом `state` и `code_challenge` (PKCE), `POST /token` отдаёт `id_token` (RS256, ключ создаётся при старте и публикуется в `jwks`) с `sub`, `email`, `email_verified`, `name`, `picture`. В `identity-service` одна переменная `GOOGLE_ISSUER_URL`: в `prod` значение `https://accounts.google.com`, в `local`/`dev` — `MOCK_GOOGLE_ISSUER_URL`, например `http://mock-google.localhost:8081`. Адрес должен открываться одинаково и браузером (он переходит на `authorize`), и контейнером `identity-service` (он читает discovery и `token`), потому что `iss` в `id_token` сверяется с издателем: в `local` имя `*.localhost` браузер сам ведёт на 127.0.0.1, а в сети Compose у `mock-google` то же имя задано как `aliases`, порт внутри и снаружи один (8081); в `dev` — то же с именем, которое разработчики резолвят до сервера. Код входа, проверка `state`, PKCE, `nonce`, поиск или создание участника и сессия — одни и те же. `config/env.ts` identity в `prod` отказывается стартовать с любым другим издателем; статическая проверка `docker compose config` в CI подтверждает, что в `prod` нет сервиса `mock-google`.

**Rationale**: FR-132 требует, чтобы путь входа не ветвился по окружению и чтобы обходных эндпоинтов не было; `openid-client` читает конечные точки из discovery, поэтому подмена издателя — единственное различие, и оно лежит в конфигурации, а не в коде. Тот же сервис подойдёт для Playwright (`E2E_TARGET=local`): тест выбирает участника на странице `mock-google`.

**Alternatives considered**:

- `POST /v1/auth/dev-login` под флагом. Прямо запрещён FR-132: флаг однажды окажется включённым в `prod`.
- Готовые контейнеры (`navikt/mock-oauth2-server`, Keycloak). Работают, но тянут чужую модель пользователей; список seed-участников пришлось бы дублировать в их конфигурации и держать в синхроне.
- Реальный Google с тестовыми учётками. Нельзя запустить без интернета и ключей, непригоден для CI и SC-026.

### 35. Устройство seed

**Decision**: `packages/seed-data` — чистые функции без доступа к БД и сети: из профиля (`small`, `large`) и якоря времени возвращают наборы записей для каждой сущности. Идентификаторы — UUIDv5 в фиксированном пространстве имён от ключа вида `article:small:017`, поэтому у записей один и тот же id в каждой базе и при каждом запуске; случайное — только из PRNG (`mulberry32`) с фиксированным зерном. Профиль `large` — надмножество `small`: id малого набора остаются теми же, добавляются 500+ опубликованных статей и тысячи комментариев с реакциями. Каждый сервис с данными имеет `src/seed/seed.ts`: читает `seed-data`, берёт из набора только свои сущности и свои копии чужих полей, пишет в свою базу через свои repository одним батчем транзакций (`INSERT … ON CONFLICT (id) DO NOTHING`, пачками по 1000 строк для большого профиля). События не публикуются: seed пишет и владельцев, и копии, а счётчики, репутацию и копии полей берёт из производных значений `seed-data`, так что системы согласованы без прохода по брокеру. Тест согласованности пересчитывает счётчики и репутацию владельцем и сверяет с записанными. Seed не обновляет и не удаляет строки, которых не создавал (определяется принадлежностью id к пространству имён UUIDv5 и таблицей `seed_runs`); конфликт по короткому адресу с не-seed строкой пропускает запись и пишет предупреждение, поэтому адреса seed имеют вид `seed-…`.

**Rationale**: FR-127 просит согласованные ссылки между сервисами — при общих детерминированных идентификаторах это достигается без вызовов между сервисами; `node-microservices.mdc` запрещает писать в чужую базу и держать бизнес-логику в `packages/*`. FR-129 требует идемпотентность и неприкосновенность чужих данных — `ON CONFLICT DO NOTHING` по фиксированному id. Публикация событий для 500+ статей и тысяч комментариев превратила бы seed в нагрузочный тест брокера и сломала бы повторяемость.

**Alternatives considered**:

- Seed через публичные HTTP-контракты (создать участника, статью, комментарий). Проверяет контракты, но при тысячах записей медленный, а время и идентификаторы не детерминированы.
- Один скрипт, пишущий во все базы. Нарушает database-per-service.
- Случайные данные (`faker` без зерна). Прямо противоречит FR-129.
- Дамп SQL в репозитории. Расходится со схемой при первой же миграции.

### 36. Время в seed, порядок запуска и prod-минимум

**Decision**: Время seed считается от якоря `anchor_at`. При первом запуске в базе якорь — начало текущего дня UTC, он записывается в `seed_runs`, и все повторные запуски используют записанное значение; `--anchor=<ISO>` задаёт его явно (тесты и CI пользуются им и получают побайтно одинаковые данные). Смещения записей от якоря фиксированы: «действующее» продвижение заканчивается через несколько дней после якоря, «истёкшее» — раньше якоря, участник с «годом на площадке» создан за 400 суток до якоря. Оркестратор `infra/scripts/seed.ts` читает `APP_ENV` и в `prod` завершается с ошибкой, не запустив ни одного сервиса; тот же `APP_ENV` проверяет `seed.ts` каждого сервиса до открытия соединения на запись — защита глубины. Порядок: `identity`, `content`, `discussion`, `messaging`, `notification`, `media` (последний загружает в MinIO несколько сгенерированных изображений с фиксированными именами объектов; большой профиль на них же ссылается). Seed идёт одноразовыми контейнерами `docker compose run --rm <service> node dist/seed.js --profile small|large`. `pnpm local` = `infra:up local` + `infra:seed local small` (SC-026).

Prod-минимум — отдельная команда `pnpm infra:bootstrap-prod`: в `identity` через use case создаёт строку суперадминистратора с `email = SUPERADMIN_EMAIL`, `role = superadmin`, `google_sub = null` и событием `identity.user.created` в outbox (профиль создаст `content-service` по событию); в `content` — строку настроек по умолчанию, если её нет. Первый вход через Google привязывает `sub` к этой строке, если почта подтверждена (`email_verified`) и совпала с назначенной. Повторный запуск ничего не дублирует: поиск по почте и `id = 1` для настроек.

**Rationale**: Без якоря «продвижение действует» и «Популярное = последние 7 суток» протухают через неделю после записи в репозиторий; якорь записывается, поэтому повторный запуск не меняет данные (FR-129). Ошибка до первой записи (FR-128) нужна и на уровне оркестратора, и на уровне сервиса: сервис можно запустить напрямую. Минимум для prod повторяет уже принятое решение №14: учётка суперадминистратора существует до первого входа.

**Alternatives considered**:

- Фиксированная календарная дата вместо якоря. Строго детерминирована, но через неделю в `local` и `dev` пусто в «Популярном», а действующих продвижений нет.
- Якорь «сейчас» при каждом запуске. Ломает идемпотентность: время записей другое.
- Считать суперадминистратора только при первом входе (без bootstrap). Не выполняет FR-128: команда для prod должна существовать и работать до входа.
- Seed в prod с флагом «подтверждаю». Нарушает FR-128.
