# Research: Вход через Firebase, вид реакций и каркас страницы

Решения, без которых план спорил бы сам с собой. Все пункты закрыты: в Technical Context плана не осталось NEEDS CLARIFICATION.

## 1. Поправка конституции

**Decision**: До слияния фичи конституция становится 2.0.0 (MAJOR: переопределены ворота принципа III и принципа V). Дата Last Amended — день правки. В начале файла на время ревью остаётся Sync Impact Report, перед коммитом он удаляется, как требует Governance. Вместе с конституцией правится `.cursor/rules/session-security.mdc`: абзац про единственный Google и `mock-google` приводится к новому тексту. Пока файл конституции не изменён, Complexity Tracking в [plan.md](./plan.md) — единственное основание не считать расхождение молчаливым.

Заменяется абзац принципа III «Вход — только Google OIDC…»:

> Вход — Firebase Authentication проекта площадки: почта с паролем, Google, GitHub и любой другой способ, включённый в том же проекте. Сессия площадки — cookie `gateway`. Токен Firebase в браузере не хранится. Обходного эндпоинта входа нет ни под каким флагом. В `local` и `dev` издателем может быть эмулятор Firebase Auth; контейнер эмулятора есть только там. В `prod` `identity-service` не стартует, если задан эмулятор или издатель ID-токена отличается от `https://securetoken.google.com/<FIREBASE_PROJECT_ID>`. Код входа и сессий один во всех окружениях. Приватный ключ сервисного аккаунта и серверный ключ API в репозиторий и в `VITE_*` не попадают.

Заменяется предложение принципа V про 1200px и одну колонку. Абзац целиком:

> Публичные разделы и администрирование живут в одной оболочке. Маршрутизатор меняет только центр. Шапка и те боковые столбцы, которые видны на этой ширине, остаются смонтированными при переходе и присутствуют в первом кадре прямой ссылки. На ширине от 1280px содержимое — полоса 1280px по центру окна: левый столбец 220px, правый 320px, просветы входят в 1280. Прокручивается страница; шапка и видимые столбцы остаются на экране. Пустой правый столбец на этой ширине сохраняет 320px. Ниже 1280px правый столбец скрыт и не переносится под центр. От 768 до 1279px левый столбец 220px остаётся. Ниже 768px одна колонка, левая навигация открывается из шапки. Отдельного приложения для телефона нет.

Остальные принципы, включая запрет секретов в браузере и закрытый состав `infra/`, не ослабляются.

**Rationale**: Конституция выше спецификации, пока её не поправили. Спецификация 002 сама называет заменяемые правила. Запись в Complexity Tracking без текста поправки оставила бы ворота в двух смыслах.

**Alternatives considered**: Молча нарушить конституцию — блокирует слияние по Governance. Удержать Google-only и 1200px — отменяет фичу. Вынести вход в новый сервис — у учётки два владельца и вторая проверка сессии.

## 2. Кто говорит с Firebase

**Decision**: Два канала, одна сессия.

- Почта, регистрация, сброс пароля и подтверждение адреса выполняет `identity-service` через Firebase Auth. Пароль приходит на `gateway` в теле POST и уходит в identity. В лог он не попадает: `req.body.password`, `*.id_token`, `*.oob_code` остаются в redact. Длина пароля (не короче 8) и форма адреса проверяются до вызова Firebase. Закрытая регистрация проверяется до создания пользователя Firebase.
- Google, GitHub и любой другой включённый провайдер открываются в окне из браузера (`signInWithPopup`). SDK поднимается с `inMemoryPersistence`, получает ID-токен, отдаёт его в `POST /v1/auth/sessions` и сразу вызывает `signOut`. Токен не пишется в `localStorage`, `sessionStorage`, IndexedDB и URL. Полная перезагрузка страницы для входа не нужна, поэтому несохранённый текст редактора и комментария остаётся.
- Сессию площадки создаёт только identity: после проверки ID-токена или после верного пароля на `POST /v1/auth/sessions`. Регистрация и подтверждение письма сессию не ставят. Cookie ставит gateway. В браузер `session_id` не возвращается.
- Список кнопок — `GET /v1/auth/config`. Его собирает identity из конфигурации проекта Firebase (серверный ключ), кэш в памяти процесса на 60 с. Отдельного списка провайдеров в настройках площадки нет.
- Веб-ключ для SDK (referrer-ограничение на origin площадки) и серверный ключ для REST (без referrer, только у identity) — разные переменные. Приватный ключ сервисного аккаунта — третья, только у identity. Ни одна не коммитится и не попадает в `VITE_*`.
- В консоли проекта обязательны: минимальная длина пароля 8 и защита от перебора адресов. Иначе публичный веб-ключ позволяет обойти нашу проверку прямым вызовом Identity Toolkit. Наша проверка длины всё равно стоит перед серверным вызовом.

SDK грузится динамическим `import()` при открытии панели, чтобы не входить в бюджет начального JS 200 KB gzip.

**Rationale**: Общий OAuth «любой провайдер, включённый оператором» умеет клиент Firebase: идентификатор провайдера приходит из конфигурации проекта, а `OAuthProvider(id)` не требует отдельной реализации GitHub, Apple и следующих. Пароль через наш сервер нужен, чтобы закрытая регистрация и длина 8 срабатывали до появления пользователя Firebase. Окно провайдера, а не переход на весь экран, совпадает с краем спецификации «закрыл окно — раздел тот же».

**Alternatives considered**: Весь вход только через SDK — пароль и создание учётки Firebase не проходят нашу границу, закрытая регистрация опаздывает. Весь вход только на сервере — на каждый провайдер свой OAuth, и кнопка «что включили в консоли» не появляется сама. `signInWithRedirect` — выгружает страницу и теряет несохранённый текст. `browserLocalPersistence` — пишет токен в IndexedDB, это запрещено.

## 3. Одна почта — один участник

**Decision**: Платформенный участник не равен пользователю Firebase. Связь хранит `auth_identities`: `firebase_uid` уникален, у участника строк может быть несколько. Почта участника уникальна без учёта регистра. Решение принимает чистая функция `decideSignIn` до записи:

| Уже есть uid | Подтверждённая почта совпала с участником | Регистрация | Результат |
| --- | --- | --- | --- |
| да | да, тот же участник | любая | Вход. Имя и аватар профиля не меняются |
| да | да, другой участник | любая | Вход в учётку, к которой уже привязан uid. Её почта не подменяется, uid к чужой учётке не переносится, вторая строка не создаётся. Экран не говорит, что адрес занят |
| нет | да | любая, включая закрытую | Вход в эту учётку, uid дописывается. Роль и ограничение остаются |
| нет | нет, почта подтверждена | открыта | Новый участник. Уже созданная строка `bootstrap-prod` с этой почтой сюда не попадает: её открывает строка «почта совпала», в том числе при закрытой регистрации |
| нет | нет | закрыта | Отказ `registration_closed`, и если почта подтверждена, но ещё ничья, и если её нет. Строка участника не создаётся. Пользователь Firebase, только что созданный окном провайдера и ни к кому не привязанный, удаляется |
| нет | почта не подтверждена | открыта | Новый участник с сессией, `email` пустая, `email_verified = false`. Неподтверждённый адрес из токена в `users.email` не пишется и чужую учётку не открывает |

Гонка двух первых входов с одной новой подтверждённой почтой упирается в уникальный индекс почты. Проигравший вставка читает победителя и привязывает свой uid к нему. На площадке остаётся одна строка.

Имя профиля пишется один раз, в `identity.user.created`: имя поставщика, для одной почты — часть адреса до `@`, не длиннее 50 символов. Повторный вход событие с новым именем или чужим аватаром не публикует.

Неподтверждённый участник получает сессию. Служебный контекст несёт `email_verified`. Предикат в `packages/contracts` отклоняет мутации участника (публикация, комментарий, реакция, подписка, закладка, сообщение, правка профиля), пока флаг ложный. Чтение, выход, повтор письма и указание почты на площадке остаются. Ограничение проверяется раньше и объясняет отказ своим текстом.

Регистрация почтой и паролем в эту таблицу не входит: у неё нет токена и нет уже известного uid. Её нейтральный ответ — решение 8.

**Rationale**: Firebase может склеить провайдеров в один uid или оставить два. Спецификация требует склейку по подтверждённой почте на нашей стороне, в момент входа, и запрещает склейку без подтверждения. Уникальная почта делает гонку наблюдаемой и тестируемой.

**Alternatives considered**: Ключ участника = `firebase_uid` — два провайдера с одной почтой становятся двумя участниками, если Firebase их не склеил. Склейка только средствами консоли Firebase — скрытая почта GitHub присоединилась бы сама, спецификация это запрещает. Отказ в сессии до подтверждения почты — человек не видит, что письмо нужно отправить ещё раз, из той же учётки.

## 4. Эмулятор вместо mock-google

**Decision**: В `local` и `dev` Compose поднимает контейнер эмулятора Auth и не поднимает `mock-google`. `identity-service` проверяет токены эмулятора, когда задан `FIREBASE_AUTH_EMULATOR_HOST`. В `prod` эта переменная запрещена на старте, контейнера в compose нет, издатель токена обязан быть `https://securetoken.google.com/<проект>`.

Тестовые участники seed входят тем же `POST` почты. Пароль seed задаёт `SEED_AUTH_PASSWORD` в env `local` и `dev` и не коммитится. `GET /v1/auth/config` в режиме эмулятора дополнительно отдаёт список адресов seed и этот пароль, чтобы панель показывала прежний выбор участника в один жест. В `prod` поля нет; старт с эмулятором или с отдачей тестового пароля запрещён. Отдельного маршрута `/v1/auth/dev-login` нет.

Письма в `local` не уходят наружу. Код подтверждения и сброса тест читает у эмулятора (`oobCodes`) и приносит его на страницу действия. В боевом проекте письмо отправляет Firebase.

Маршруты `GET /v1/auth/google` и `GET /v1/auth/google/callback` удаляются.

**Rationale**: FR-013 требует тот же код сессии и тестовый вход без настоящего поставщика. Подмена издателя уже была принятым способом для `mock-google`. Эмулятор — тот же приём для Firebase.

**Alternatives considered**: Оставить `mock-google` рядом с Firebase — два входа и издатель, который prod-проверка больше не ждёт. Боевой проект Firebase на машине разработчика — без сети и без консоли тест не идёт, а «без настоящего поставщика» не выполняется. Эндпоинт, который сразу ставит сессию seed-участнику, — обходной вход под флагом.

## 5. Геометрия каркаса

**Decision**: Один и тот же `Shell` на всех разделах из контракта разделов фичи 001.

- Окно ≥ 1280px: полоса `width: 1280px; margin-inline: auto`. Колонки `220px minmax(0, 1fr) 320px`, `column-gap: 16px`. Оба просвета входят в 1280, центр получает 708px. Поля окна по бокам — фон страницы.
- Окно 768–1279px: колонки на всю ширину окна `220px minmax(0, 1fr)`, тот же просвет 16px. Правого столбца в потоке нет (`display: none`), в том числе пустого. Под центр он не переносится.
- Окно < 768px: одна колонка. Кнопка шапки открывает ту же левую навигацию. Правого столбца нет.
- Прокручивается документ. Класс `shell-lock` и высота `100dvh` у колонки снимаются. Шапка `position: sticky; top: 0` высотой 56px. Видимый боковой столбец: `position: sticky; top: 56px; max-height: calc(100dvh - 56px); overflow-y: auto; align-self: start`. Так список тем крутится внутри левого столбца, а длинный центр уезжает вместе со страницей, оставляя шапку и второй столбец на месте.
- Видимость столбцов задаёт CSS, не `matchMedia` после гидрации, чтобы прямой адрес в первом кадре показывал те столбцы, которые положены ширине.
- Левый столбец больше не карточка: пункты лежат на фоне страницы, текущий пункт отмечен. Правый — стопка скруглённых карточек; обязательная карточка — «Популярные комментарии». Пустая на широком экране держит 320px.
- «Наверх» крутит `window`. Положение возврата в ленту пишется из `window.scrollY` в тот же `sessionStorage`, что и раньше.
- Шапка в одну строку: знак площадки; для раздела с названием — назад, название одной строкой с многоточием, обновление данных центра; затем кнопка поиска, уведомления, «Написать», аватар. Кнопка поиска стоит сразу перед уведомлениями на широком экране, на планшете и на телефоне и не уезжает в центр шапки. Обновление сбрасывает запросы центра и не размонтирует шапку.
- Комментарии статьи живут в центре. Скрытие правого столбца их не удаляет. Блок «Подписка Plus» и прочая реклама прототипа не добавляются.

Пороги в существующих e2e (константа 1200 и скролл `[data-shell-scroll="center"]`) переносятся на документ и на 1280 / 768.

**Rationale**: Текущий `Shell` фиксирует окно и на ≥ 1200px отдаёт прокрутку только центру, а ниже 1200px ставит правую карточку под центр. Это ровно то, что спецификация отменяет. Липкие столбцы при прокрутке документа дают и неподвижную шапку, и независимую прокрутку длинного списка слева.

**Alternatives considered**: Оставить внутренний скролл и только поменять числа 1200 → 1280 — правый столбец на планшете останется под статьёй, страница по-прежнему не крутится. Прятать правый столбец скриптом по `useMediaQuery` — первый кадр прямой ссылки зависит от эффекта и мигает.

## 6. Вид реакции

**Decision**: Четыре вида `laugh | heart | thumb | fire` не меняются и не получают пятого. У каждой настройки ровно один показ: `{ kind, presentation: 'emoji' | 'image', emoji, image_url }`. Пока суперадминистратор не сохранял, значения совпадают с сегодняшними `😄 ❤️ 👍 🔥`.

Хранит `content-service` в строке настроек площадки. `GET /v1/settings` отдаёт вид всем, включая гостя. `PUT /v1/settings` по-прежнему только для `superadmin`; администратор получает 403. Пустой эмодзи, не один эмодзи и чужой адрес картинки не сохраняются, прежний вид остаётся, ответ объясняет поле.

Один эмодзи — одна графема (`Intl.Segmenter`), и эта графема — эмодзи. Склейка ZWJ из нескольких кодпоинтов, которую сегментатор считает одной графемой, допустима. Две графемы и обычное слово — нет.

Картинка загружается тем же `POST /v1/media?kind=image`, что логотип, и проходит тот же `assertMediaUrl`. Файл в настройках не хранится, хранится адрес.

Клиент рисует ряд, меню выбора и популярные комментарии из этого ответа, а не из зашитого `REACTION_EMOJI`. Текстовое имя для читалки экрана берётся из прежних ключей переводов. Если адрес картинки не загрузился, на кнопке видно это имя, поставить и снять реакцию можно. Числа и `my_reaction` приходят как раньше из `discussion` и этой настройкой не переписываются.

Уже открытая вкладка: `gateway` превращает `content.settings.updated` в кадр `settings` для каждого соединения потока. Клиент инвалидирует ключ публичных настроек и перечитывает их. Статьи заново не публикуются.

Поле в событии v1 необязательное, чтобы старый потребитель флагов регистрации (identity) не отвергал конверт. HTTP-ответ настройки содержит поле всегда.

**Rationale**: Картинка — оформление площадки, его меняет тот же человек, что логотип. Строка «кто поставил» принадлежит обсуждению и при смене картинки не должна обновляться. Отдельный ресурс настроек плодил бы второй запрос и второе событие на одно сохранение формы.

**Alternatives considered**: Колонки картинок в `discussion` — смена вида писала бы не в ту базу и выглядела бы как смена поставленных реакций. Отдавать картинку внутри каждой карточки ленты — смена вида требовала бы пересборки ленты, а открытая страница не обновилась бы без нового события статьи. Пятый вид «лайк» — спецификация запрещает.

## 7. Служебный контекст `email_verified`

**Decision**: В `serviceContextSchema` и claims JWT добавляется `email_verified: boolean` со значением по умолчанию `true`, если поля нет. Новый identity всегда пишет фактическое значение. Мутации участника вызывают общий предикат и при `false` отвечают `email_unverified`. Гость и чтение публичного предиката не касаются.

Копии пользователя в `content` и `discussion` этот флаг не хранят: он и так в каждом служебном JWT, который gateway собирает из сессии.

**Rationale**: Правило «нельзя комментировать, пока почта не подтверждена» принадлежит владельцам мутаций, не gateway. Значение по умолчанию не рвёт JWT, выпущенный за секунду до выкладки (TTL не больше 60 с). Обязательное поле без умолчания отвергло бы старый процесс со `strictObject` на всё окно выкладки.

**Alternatives considered**: Проверять только в gateway по списку маршрутов — бизнес-правило уезжает в прокси. Хранить флаг копией — лишнее событие и окно, в котором копия врёт. Не пускать неподтверждённого в сессию — расходится с FR-006, ему нужно оставаться на площадке, указать почту и запросить письмо ещё раз.

## 8. Нейтральный ответ и почта, указанная на площадке

**Decision**: Два экрана, которые спецификация запрещает отличать от успеха, отвечают одним и тем же телом и не открывают чужую учётную запись.

Регистрация `POST /v1/auth/registrations` при открытой регистрации всегда отвечает одним нейтральным документом `{ status: 'pending' }` без `Set-Cookie` и без сессии. Свободный адрес: создаются пользователь Firebase и строка участника, `email` записана, `email_verified = false`, уходит письмо. Адрес, который уже есть у участника: вторая строка не создаётся, пользователь Firebase не создаётся, письмо не уходит, тело и статус ответа те же. Текст не предлагает войти и не говорит, что адрес занят. Сессия появляется только следующим `POST /v1/auth/sessions`. Подтверждение письма сессию само не ставит: SC-001 считает регистрацию, подтверждение и вход тремя шагами. Гонка двух регистраций на один свободный адрес упирается в уникальный индекс; проигравший удаляет своего только что созданного и ни к кому не привязанного пользователя Firebase и отдаёт тот же `pending`.

При закрытой регистрации любой адрес, новый или уже существующий, получает один и тот же `registration_closed`. Это не нейтральный экран успеха и адрес по нему не угадывается.

Участник без подтверждённой почты, уже держащий сессию, указывает адрес на площадке: `POST /v1/auth/email-claims`, тело `email`. Непохожий на почту адрес объясняют у поля, строка не меняется. Похожий адрес всегда отвечает тем же `{ status: 'pending' }`. Свободный адрес записывается в `users.email`, `email_verified` остаётся ложью, уходит письмо. Адрес другого участника не записывается, письмо не уходит, действия участника остаются закрытыми, и экран не говорит, что адрес занят. Повтор того же своего неподтверждённого адреса только отправляет письмо ещё раз и выглядит так же. Уже подтверждённая почта этим маршрутом не подменяется.

Код из письма принимает `POST /v1/auth/email-verification-confirmations` без обязательной сессии: письмо открывают в другом браузере. Код применяется к пользователю Firebase, платформенная строка с его uid получает `email_verified = true`. Чужой и просроченный код учётку не подтверждают и не сообщают, чья она. Если cookie этой же учётки уже есть, следующие запросы видят истину в служебном контексте.

**Rationale**: Успех регистрации, который сразу ставит сессию, нельзя повторить для занятого адреса, не войдя в чужую учётку. Общий `pending` без cookie совпадает с FR-009 и SC-009 и оставляет вход отдельным шагом. Указание почты на площадке — единственный путь FR-006 для способа, который подтверждённый адрес не прислал; тот же `pending` закрывает перебор адресов на этом шаге.

**Alternatives considered**: Отказ `email_taken` и текст «войдите» — экран отличается от обычной регистрации, спецификация это запрещает. Открыть сессию занятого адреса — вход в чужую учётку. Письмо владельцу «кто-то регистрировался на ваш адрес» — экран не меняет, но спецификация его не требует, отдельная отправка расходится по времени с пустым успехом. Хранить неподтверждённый адрес из токена GitHub сразу в `users.email` — это уже привязка до письма, а занятый адрес тогда нельзя принять тем же ответом, не задев уникальный индекс чужой строки.
